## 1️⃣ Old Redux (Classic Way)

### 🔹 Action Types
```
API Data (Redux) → Original state
          ↓
Derived copy (map) → UI-specific modifications
          ↓
Global changes? → dispatch Redux action to update original state
```

```javascript
actionTypes.js 
export const INCREMENT = "INCREMENT"; 
export const DECREMENT = "DECREMENT";
export const SUCCESS = "SUCCESS";
```
---

### 🔹 Actions

```javascript
// actions.js 
import { INCREMENT, DECREMENT, SUCCESS } from "./actionTypes";  
export const increment = () => ({   type: INCREMENT });  
export const decrement = () => ({   type: DECREMENT });  
export const success = (payload) => ({   type: SUCCESS,   payload });
```

---

### 🔹 Reducer

```javascript
// reducer.js 
import { INCREMENT, DECREMENT, SUCCESS } from "./actionTypes";  
const initialState = {   count: 0,   data: null };  
export default function counterReducer(state = initialState, action) {
   switch (action.type) {     
	   case INCREMENT:       
		   return { ...state, count: state.count + 1 };      
	   case DECREMENT:       
		   return { ...state, count: state.count - 1 };      
	   case SUCCESS:       
		   return { ...state, data: action.payload };      default:       return state;
	   } 
}
```

---

### 🔹 Store

```javascript
// store.js 
import { createStore } from "redux"; 
import counterReducer from "./reducer";
  
const store = createStore(counterReducer);
  
export default store;
```

### Used: (Same, Old Redux and Redux Tool Kit):
```javascript
// Dispatch an action  
store.dispatch(increment()); // calls reducer  
store.dispatch(success({ name: "Ali" })); // calls reducer
```

## 2️⃣ Redux Toolkit (Slice Way – Modern Redux)

> **Everything above collapses into ONE file**

---

### 🔹 Slice (Actions + Types + Reducer together)

```javascript
// counterSlice.js
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: {
    count: 0,
    data: null,
  },
  reducers: {
    increment(state) {
      // looks mutable, but safe (Immer)
      state.count += 1;
    },
    decrement(state) {
      state.count -= 1;
    },
    success(state, action) {
      state.data = action.payload;
    },
  },
});

export const { increment, decrement, success } = counterSlice.actions;
export default counterSlice.reducer;
```

---

### 🔹 Store

```javascript
// store.js
import { configureStore } from "@reduxjs/toolkit";
import counterReducer from "./counterSlice";

/*  
Explanation:  
1. `counterSlice.reducer` is the actual reducer function created by createSlice.  
2. In store.js, we import it as `counterReducer` (local name, can be anything).  
3. The `counter` key in the reducer object defines the slice of state:  
state.counter → holds { count, data } managed by counterReducer.  
4. Actions (increment, decrement, success) are exported separately to dispatch updates.  
*/

export const store = configureStore({
  reducer: {
    counter: counterReducer,
  },
});
```

---

## 3️⃣ Side-by-Side Concept Mapping (THIS IS THE KEY PART)

|Old Redux|Redux Toolkit Slice|
|---|---|
|`actionTypes.js`|**Auto-generated**|
|`INCREMENT`|`"counter/increment"`|
|Action creator|Generated by `createSlice`|
|`switch(action.type)`|Reducer functions|
|Immutable updates|Immer (write mutable code)|
|Multiple files|Single slice file|
### ✅ TL;DR

|Feature|Old Redux|Redux Toolkit|
|---|---|---|
|Action types|Manual string constants|Auto-generated from slice|
|Action creators|Manual|Auto-generated from slice|
|Reducer|Manual switch-case|Defined inline in slice|
|Dispatch|`store.dispatch(action)`|Same|
|Immutability|Manual (`...state`)|Automatic via Immer|

---

Basically, **dispatching actions looks identical**, but **Redux Toolkit simplifies creating the actions and reducer**

> `createAsyncThunk` = **pre-written SUCCESS / ERROR / LOADING boilerplate**

It replaces this **old Redux pattern** 👇

### Old Redux Async Pattern

`FETCH_START FETCH_SUCCESS FETCH_ERROR`

`pending fulfilled rejected`

## 3️⃣ Redux Toolkit WITHOUT `createAsyncThunk` (Perfectly Valid)

### Slice

`const userSlice = createSlice({   name: "user",   initialState: {     user: null,     loading: false,     error: null   },   reducers: {     fetchStart(state) {       state.loading = true;     },     fetchSuccess(state, action) {       state.loading = false;       state.user = action.payload;     },     fetchError(state, action) {       state.loading = false;       state.error = action.payload;     }   } });  export const {   fetchStart,   fetchSuccess,   fetchError } = userSlice.actions;`

### Async Logic (Manual – Old Style)

`export const fetchUser = () => async (dispatch) => {   dispatch(fetchStart());   try {     const res = await fetch("/api/user");     const data = await res.json();     dispatch(fetchSuccess(data));   } catch (err) {     dispatch(fetchError(err.message));   } };`

➡️ **This is 100% Redux Toolkit + old Redux thinking**

---

## 4️⃣ Redux Toolkit WITH `createAsyncThunk` (Cleaner)

`export const fetchUser = createAsyncThunk(   "user/fetchUser",   async () => {     const res = await fetch("/api/user");     return res.json();   } );`

`extraReducers: (builder) => {   builder     .addCase(fetchUser.pending, (state) => {       state.loading = true;     })     .addCase(fetchUser.fulfilled, (state, action) => {       state.loading = false;       state.user = action.payload;     })     .addCase(fetchUser.rejected, (state, action) => {       state.loading = false;       state.error = action.error.message;     }); }`

---

## 5️⃣ When SHOULD you use `createAsyncThunk`?

Use it when:  
✔ Standard API calls (CRUD)  
✔ You want less boilerplate  
✔ SUCCESS / ERROR / LOADING pattern  
✔ You don’t need complex side effects

---

## 6️⃣ When NOT to use `createAsyncThunk`?

Avoid or skip it when:  
❌ Very complex async flows  
❌ Multiple chained API calls  
❌ WebSocket / polling logic  
❌ You want full manual control  
❌ Logic already handled in service layer

In these cases:

- manual thunk
    
- RTK Listener Middleware
    
- React Query / TanStack Query
    

are often **better choices**

Redux Toolkit says:

> “Use it if it helps — ignore it if it doesn’t.”

You can safely mix:

- slices
    
- manual thunks
    
- old Redux patterns

## What is React Query? (Simple)

**React Query is a tool for fetching server data.**

That’s it.

Not for:

- UI state
    
- form state
    
- modal open/close
    

Only for **data that comes from the backend**.

---

## The Problem It Solves

Without React Query, you usually do this:

- loading state
    
- error state
    
- fetch API
    
- cache response
    
- refetch when needed
    
- keep data in sync
    

You manually manage all of that.

**React Query does this automatically.**

---

## What React Query Does For You

Think of it as a **smart data manager**:

- fetches data
    
- caches it
    
- avoids duplicate requests
    
- refetches when needed
    
- keeps data fresh
    
- handles loading & error states
    

---

## Simple Mental Model

`Server data lives in React Query UI just asks for it`

You **don’t store API data in Redux** anymore.

---

## When You Use React Query

Use it for:

- GET requests
    
- backend data (products, users, orders)
    
- data that must stay in sync with server
    

---

## When You DON’T Use It

Don’t use it for:

- form inputs
    
- modal open/close
    
- theme
    
- local UI flags
    

Those belong in:

- component state
    
- Redux (if global)
    

---

## Redux vs React Query (Very Simple)

|Redux|React Query|
|---|---|
|UI & app state|Server state|
|Manual loading|Auto loading|
|Manual caching|Auto caching|
|Reducers|No reducers|
|Actions|No actions|

---

## Simple Example (Concept Only)

Instead of:

- dispatch fetch
    
- handle loading
    
- save to store
    

You do:

- “give me users”
    
- React Query handles the rest
    

---

## One Sentence Summary

> **Redux manages your app state**  
> **React Query manages your server data**

---

## Final Rule of Thumb

If data comes from **API** → **React Query**  
If data controls **UI behavior** → **Redux / local state**

## Why installation is required

React only gives you:

- `useState`
    
- `useEffect`
    
- basic hooks
    

React Query is a **separate library** that provides:

- caching
    
- background refetching
    
- request deduplication
    
- server-state management
    

So React **cannot do this by default**.

---

- you don’t want to manage loading/error/caching yourself

- **Mostly CRUD APIs** → ✅ install
